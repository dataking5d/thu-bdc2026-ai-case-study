# 项目案例与复盘

## 问题与验收目标

任务背景是基于沪深300成分股历史行情，预测并输出股票代码和组合权重。历史实现采用 LightGBM 回归打分、横截面标准化、风险过滤和 Top-5 组合构建。

我将验收拆成三个层次：标签是否对应题目中的买卖时点；模型比较是否使用同一评分口径；推理产物是否能被交付入口读取。

## 我与 AI 怎样分工

依据本人已确认的履历，我负责建模思路、任务要求、测试、结果判断和优化方向；AI Agent 承担代码实现与优化。现有文件能证明相关程序和实验记录存在，但不能还原每一次人机对话，也不证明每行代码均由我独立编写。

## 三个有证据的决策节点

### 1. 先核对目标，再解释分数

历史 `build_labels()` 同时保留两种口径：旧版 `(open[t+5]-open[t])/open[t]`，修正版 `(open[t+5]-open[t+1])/open[t+1]`。代码可以直接核对；修正版与赛事规则的对应关系来自历史记录，本轮未重新检索官方规则页。

差别在于买入时点。用错目标训练，即使研究指标很高，也不能直接说明完成了比赛任务。后续实验按标签版本区分，旧指标不再用来证明修正模型的效果。

### 2. 用验证约束增加复杂度

历史研究尝试事件、热度、资金流、网络等模块。7月冻结记录曾保留 Event Core，拒绝或暂缓部分模块；这些是历史实验决策，不代表对任何市场环境都成立。

部分模块代码保留在本地，不随本公开仓库发布；不把“探索过”写成“全部有效”。7月和8月的文件并不完全一致，复盘必须标注具体版本。

### 3. 将模型结果转成可交付产物

本地整理后的历史提交目录包含训练、推理、特征处理与 Docker 入口，特征列 JSON 用于锁定输入顺序。公开包只展示精选实验记录与输出，输出采用 `stock_id,weight` 两列。

但脚本和目录存在不等于比赛平台验收通过。B 阶段最终未提交，也没有本轮完整容器复现结果，因此这里展示的是交付准备及其不足。

## 具体交付物

| 交付物 | 能说明什么 | 不能说明什么 |
|---|---|---|
| 历史训练/推理代码与特征列 | 任务已形成程序流程 | 不证明全部路径可运行或没有数据泄漏 |
| 7月实验 JSON | 保存过本地评估结果 | 不等于官方分数或完整重跑 |
| 8月预测输出与元数据 | 输出格式和版本追踪材料存在 | 不等于平台提交成功 |
| 本轮人工数据演示 | 部分历史函数在隔离样例下可执行 | 不证明模型预测能力 |

## 如果重做

先固定题目原文、标签和输出合同，再建立一个小基线；为每次实验绑定数据、标签、特征、评估版本；设置停止探索和提交缓冲时间；最后在干净环境按平台入口完整跑一遍。

错过 B 阶段提交说明，实验优化不能替代截止时间管理。对我希望参与的 AI 应用、业务分析和项目交付工作，这段经历最值得迁移的是：把模糊任务变成检查项，审查 AI 输出，及时终止证据不足的方向，并为交付留出时间。
